# OutboxPattern.Domain

## 1. Назначение

Проект `OutboxPattern.Domain` содержит доменную модель приложения для управления заказами покупателей.

Доменный слой отвечает за представление бизнес-сущностей, их состояния и правил, определяющих допустимое поведение системы.

Он не зависит от инфраструктуры, базы данных, брокеров сообщений и механизмов сериализации.

## 2. Состав проекта

Файлы доменной модели находятся в каталоге `Orders`:

```text
src/OutboxPattern.Domain/
└── Orders/
    ├── Order.cs
    └── OrderStatus.cs
```

### 2.1. `Order`

`Order` представляет заказ покупателя и инкапсулирует его состояние и бизнес-правила.

Сущность содержит следующие свойства:

| Свойство | Тип | Описание |
|---|---|---|
| `Id` | `Guid` | Уникальный идентификатор заказа |
| `CustomerEmail` | `string` | Адрес электронной почты покупателя (не более 255 символов) |
| `TotalPrice` | `decimal` | Итоговая сумма заказа |
| `Status` | `OrderStatus` | Текущий статус заказа |
| `CreatedAtUtc` | `DateTimeOffset` | Дата и время создания заказа в UTC |

Создание заказа выполняется с помощью статического метода `Create()`, который проверяет входные данные и инициализирует начальное состояние сущности.

Изменение статуса выполняется через методы `Confirm()` и `Cancel()`, которые проверяют допустимость перехода перед изменением состояния.

### 2.2. `OrderStatus`

`OrderStatus` определяет возможные состояния заказа.

| Статус | Значение | Описание |
|---|---|---|
| `Pending` | `10` | Заказ создан и ожидает подтверждения или отмены |
| `Confirmed` | `20` | Заказ подтверждён |
| `Cancelled` | `30` | Заказ отменён |

Значения кратны 10, чтобы новые статусы можно было добавлять между существующими без изменения уже сохранённых в базе данных чисел.

Новый заказ всегда создаётся со статусом `Pending`.

## 3. Бизнес-правила

### 3.1. Создание заказа

При создании заказа действуют следующие правила:

1. Адрес электронной почты покупателя не может быть пустым.
2. Адрес электронной почты не должен превышать 255 символов.
3. Адрес электронной почты должен содержать символ `@`.
4. Итоговая сумма заказа должна быть больше нуля.
5. Заказ получает уникальный идентификатор.
6. Дата и время создания фиксируются в UTC.
7. Начальный статус заказа — `Pending`.

Ограничение длины задаётся константой `Order.CustomerEmailMaxLength` и используется в EF-конфигурации.

Проверка электронной почты является упрощённой и не гарантирует полного соответствия адреса формату email.

### 3.2. Подтверждение заказа

Метод `Confirm()` переводит заказ из статуса `Pending` в статус `Confirmed`.

Подтверждение невозможно, если заказ уже подтверждён или отменён. В этом случае выбрасывается `InvalidOperationException`.

### 3.3. Отмена заказа

Метод `Cancel()` переводит заказ из статуса `Pending` в статус `Cancelled`.

Отмена невозможна, если заказ уже подтверждён или отменён. В этом случае выбрасывается `InvalidOperationException`.

## 4. Допустимые переходы состояний

На текущем этапе реализованы следующие переходы:

| Текущий статус | Операция | Результат |
|---|---|---|
| `Pending` | `Confirm()` | `Confirmed` |
| `Pending` | `Cancel()` | `Cancelled` |
| `Confirmed` | `Confirm()` | Ошибка |
| `Confirmed` | `Cancel()` | Ошибка |
| `Cancelled` | `Confirm()` | Ошибка |
| `Cancelled` | `Cancel()` | Ошибка |

Таким образом, после подтверждения или отмены заказ не может быть повторно переведён в другое состояние с помощью существующих методов.

## 5. Границы ответственности

Доменный слой отвечает за:

- хранение бизнес-состояния заказа;
- проверку бизнес-правил;
- создание заказа;
- допустимые переходы между статусами.

Доменный слой не отвечает за:

- сохранение данных в базе;
- управление транзакциями;
- формирование SQL-запросов;
- хранение сообщений Outbox;
- сериализацию интеграционных событий;
- публикацию сообщений в брокер;
- фоновую обработку сообщений.

Эти обязанности реализуются в других слоях приложения.

## 6. Принципы проектирования

При разработке доменной модели используются следующие принципы:

- бизнес-правила инкапсулируются внутри сущностей;
- состояние изменяется через методы, контролирующие допустимость операций;
- прямое изменение свойств извне ограничено;
- доменный слой не зависит от инфраструктурных технологий;
- модель расширяется по мере появления реальных бизнес-требований.

## 7. Дальнейшее развитие

В дальнейшем доменная модель может быть расширена позициями заказа, дополнительными бизнес-правилами и доменными событиями.

Эти изменения будут добавляться по мере необходимости, чтобы сохранить простоту модели и сосредоточиться на изучении паттерна Transactional Outbox.
